# 디자인 패턴 

1994년 Gan of Four로 알려진 네 명의 개발자가 정리한 객체-지향 코딩 패턴 모음집입니다. 객체-지향 시스템을 설계할 때 참조할 수 있는 다양한 해법을 제시합니다.

문제 및 배경, 실제 적용된 사례, 샘플 코드 등으로 구성되어 있습니다. 

다음의 3가지 패턴으로 구성됩니다.

- 생성 패턴 (Creational Pattern)
- 구조 패턴 (Structural Pattern)
- 행위 패턴 (Behavioral Pattern)


# 생성 패턴

객체의 생성과 참조 과정을 정의합니다

- 추상 팩토리 (Abstract Factory)
- 빌더 (Builder)
- 팩토리 메소드 (Factory Method)
- 프로토타입 (Prototype)
- 싱글톤 (Singleton)

추상 팩토리: 구체적인 클래스에 의존하지 않고 인터페이스를 통해 서로 연관/의존하는 객체들의 그룹으로 생성하여 추상적으로 표현합니다. 연관된 서브클래스를 묶어 한 번에 교체하는 것이 가능합니다.

빌더: 작게 분리된 인터페이스를 건축하듯이 조합하여 객체를 생성합니다. 객체의 생성 과정과 표현 방법을 분리하고 있어 동일한 객체 생성에서도 서로 다른 결과를 만들어 낼 수 있습니다.

팩토리 메소드: 객체 생성을 서브 클래스에서 처리하도록 분리하여 캡슐화합니다. 상위 클래스에서 인터페이스만 정의하고 실제 생성을 서브 클래스가 담당합니다. 가상 생성자 패턴이라고로 합니다

프로토타입: 원본 객체를 복제하는 방법으로 객체를 생성합니다.

싱글톤: 하나의 객체를 생성하면 생성된 객체를 어디서든 참조할 수 있지만 여러 프로세스가 동시에 참조할 수는 없습니다. 클래스 내에서 인스턴스가 오직 하나인 것을 보장하며 불필요한 메모리 낭비를 최소화할 수 있습니다


# 구조 패턴

객체들을 조합하여 더 크고 복잡한 구조를 만드는 방법을 정의합니다

- 어댑터 (Adapter)
- 브릿지 (Bridge)
- 컴포지트 (Composite)
- 데코레이터 (Decorator)
- 파사드 (Facade)
- 플라이웨이트 (Flyweight)
- 프록시 (Proxy)

어댑터: 호환성이 없는 클래스들의 인터페이스를 다른 클래스가 이용할 수 있도록 변환해합니다. 기존의 클래스를 이용하고 싶지만 인터페이스가 일치하지 않을 때 사용합니다.

브리지: 구현부에서 추상층을 분리하고 서로가 독립적으로 확장할 수 있도록 구성합니다. 기능과 구현을 두 개의 별도 클래스로 구현합니다.

컴포지트: 여러 객체를 가진 복합 객체와 단일 객체를 구분없이 다룰 수 있습니다. 객체들을 트리 구조로 구성합니다

데코레이터: 객체 간의 결합을 통해 능동적으로 객체의 기능을 확장할 수 있습니다. 임의의 객체에 부가적인 기능을 추가하기 위해 다른 객체들을 덧붙이는 방식으로 구현합니다.

파싸드: 복잡한 서브클래스들을 피해 상위의 인터페이스를 구성해서 서브 클래스들의 기능을 간편하게 사용할 수 있습니다. 서브 클래스들 사이의 통합 인터페이스를 제공하는 Wrapper 객체가 필요합니다.

플라이웨이트: 인스턴스가 필요할 때마다 매번 생성하지 않고 가능한 한 하나의 인스턴스를 공유함으로써 메모리를 절약합니다. 다수의 유사한 객체를 생성하거나 조작할 때 유용합니다.

프록시: 접근이 어려운 객체와 이 객체에 연결하려는 객체 사이에서 인터페이스의 역할을 수행하는 객체(프록시)를 생성합니다. 네트워크 연결, 대용량 객체에 접근하기 등의 목적으로 사용됩니다.


# 행위 패턴

클래스나 객체들의 상호작용 방법과 책임 분배방법 등을 정의합니다

- 책임 연쇄 (Chain of Responsibility)
- 커맨드 (Command)
- 인터프리터 (Interpreter)
- 반복자 (Iterator)
- 중재자 (Mediator)
- 메멘토 (Memento)
- 옵저버 (Observer)
- 상태 (State)
- 전략 (Strategy)
- 템플릿 메소드 (Template Method)
- 방문자 (Visitor)

책임 연쇄: 요청을 처리할 수 있는 객체가 둘 이상 존재하고 한 객체가 요청을 처리하지 못하면 다음 객체로 요청이 전달됩니다. 객체들이 체인으로 연결되어 있고 요청이 해결될 때까지 고리를 따라 책임이 넘어갑니다.

커맨드: 요청을 객체의 형태로 캡슐화하여 재이용하거나 취소할 수 있습니다. 요청에 사용되는 각종 명령어들을 추상 클래스와 구체적인 클래스로 분리하여 단순화합니다.

인터프리터: 언어의 문법 표현을 정의하는 패턴입니다. SQL이나 프로토콜 등을 개발할 때 사용됩니다

반복자: 자료 구조와 같이 접근이 잦은 객체에 대해 동일한 인터페이스를 제공합니다. 내부 표현 방법을 노출하지 않고도 순차적인 접근이 가능합니다

중재자: 수많은 객체들 간의 복잡한 상호작용을 캡슐화하여 객체로 만듭니다. 객체 사이의 의존성을 줄여 결합도를 감소시킬 수 있습니다

메멘토: 특정 시점에서 객체의 상태를 객체화함으로써 이후 요청에 따라 객체를 해당 시점의 상태으로 되돌릴 수 있는 기능을 제공합니다. 되돌리기(Ctrl+Z) 기능 등을 개발할 때 사용됩니다.

옵저버: 한 객체의 상태가 변하면 그 객체에 의존하는 다른 객체들에게 변화된 상태를 전달합니다. 일대다의 의존성을 정의합니다. 주로 분산된 시스템에서 이벤트를 처리할 때 이용됩니다.

상태: 동일한 동작을 객체의 상태에 따라 다르게 처리할 수 있습니다. 객체 상태를 캡슐화하고 이를 참조하는 방식으로 작동합니다.

전략: 동일한 계열의 알고리즘들을 개별적으로 캡슐화하고 서로 교환할 수 있게 정의합니다. 클라이언트는 원하는 알고리즘을 선택할 수 있고 클라이언트에 영향을 미치지 않고도 알고리즘을 변경할 수 있습니다.

템플릿 메소드: 상위 클래스에서 골격을 정의하고 하위 클래스에서 세부 처리를 합니다. 

방문자: 각 클래스에서 처리 기능을 분리하고 처리 담당 클래스(방문자)에 처리 기능을 전달합니다. 방문자가 각 클래스를 방문하여 처리 기능을 수행합니다
