## 실행 여부에 따른 테스트

- 정적 테스트 (Static Test)
- 동적 테스트 (Dynamic Test)


## 정적 테스트

프로그램을 실행하지 않고 `소스 코드(Source Code)`를 대상으로 하는 테스트이다. 소스 코드에 대한 코딩 표준, 코딩 스타일, 코드 복잡도, 코드 결함 등을 테스트한다. 주로 소프트웨어 개발 단계의 초반에 수행한다.

*종류*

- Inspection  
- Walkthrough  

**Walkthrough** 프로그램의 개발자가 4-5명의 다른 개발자 또는 테스터에게 어떠한 형식에 맞추어 발표한다. 발표 전 검토자들은 프로그램의 코드를 미리 받아 분석하고 질문사항을 준비한다.


## 동적 테스트

프로그램을 실행하고 테스트한다. 소프트웨어 개발의 모든 단계에서 수행하는 테스트이다.

- 화이트박스 테스트 (White-Box Test)
- 블랙박스 테스트 (Black-Box Test)


## 개발 단계에 따른 테스트 분류

테스트는 V-모델에 기반하여 분류 및 정의된다

1. 단위 테스트 (Unit Test)
2. 통합 테스트 (Integration Text)
3. 시스템 테스트 (System Test)
4. 인수 테스트 (Acceptance Test)

**V-모델**  개발 단계와 테스트 단계를 각각 4단계로 구분하고
각 테스트 단계와 테스트 대상(각 개발 단계)을 연결한 모델이다.
![v-model](./v-model.jpg)


## 단위 테스트 

구현 직후 소프트웨어 설계의 최소 단위인 `모듈이나 컴포넌트`에 초점을 맞춰 테스트하는 것이다.
인터페이스, 외부적 I/O, 자료 구조, 독립적 기초 경로, 오류 처리 경로, 경계 조건 등을 검사한다.
사용자의 요구사항을 기반으로 한 기능 테스트를 최우선으로 수행한다.
구조기반 테스트와 명세기반 테스트로 나뉘지만 주로 구조 기반 테스트를 시행한다.


## 통합 테스트 

단위 테스트가 완료된 모듈들을 결합하여 하나의 시스템으로 완성시키는 과정을 테스트한다. 모듈 간 상호작용 과정에서 발생하는 오류를 검사한다.
비점진적 통합 방식과 점진적 통합 방식이 있다

**점진적 통합 방식** 모듈을 단계적으로 통합하면서 테스트한다 

- 상향식 통합 테스트 
- 하향식 통합 테스트 
- 혼합식 통합 테스트

**비점진적 통합 방식** 단계적으로 통합/테스트하는 절차 없이 모든 모듈이 결합되어 있는 프로그램 전체를 테스트한다. 규모가 작은 프로그램을 테스트할 때 에서 주로 사용된다

- 빅뱅 통합 테스트


## 시스템 테스트

개발된 소프트웨어가 해당 컴퓨터 시스템에서 완벽하게 수행되는가를 점검한다.
기능적/비기능적 요구사항으로 구분하고 각 요구사항을 만족하는지 테스트한다.


## 인수 테스트

개발된 소프트웨어가 사용자의 요구사항을 충족하는지에 중점을 두고 테스트한다.
사용자가 직접 테스트한다.

- 알파 테스트
- 베타 테스트

**알파 테스트** 개발자의 장소에서 사용자가 개발자 앞에서 테스트한다. 
테스트는 통제된 환경에서 행해지며, 오류와 문제점을 사용자와 개발자가 함께 확인한다.

**베타 테스트** 선정된 최종 사용자가 여러 명의 사용자 앞에서 테스트한다.
실업무를 가지고 사용자가 직접 테스트한다.


## 테스트 방향 기준

통합 테스트의 방향

- 상향식 통합 테스트 (Bottom-Up Integration Test)
- 하향식 통합 테스트 (Top-Down Integration Test)
- 혼합식 통합 테스트

![stepwise-integration](./stepwise-integration.png)

## 상향식 통합 테스트

프로그램의 하위 모듈에서 상위 모듈 방향으로 통합하면서 테스트한다.

*절차*

1. 하위 모듈들을 클러스터(Cluster)로 결합한다.

2. 상위 모듈에서 데이터의 입/출력을 확인하기 위해 드라이버(더미 모듈)를 작성한다.

3. 통합된 클러스터 단위로 테스트한다.

4. 테스트가 완료되면 드라이버는 실제 모듈로 대체되고 클러스터는 프로그램 구조의 상위로 이동한다.

**테스트 드라이버(Test Driver)** 테스트 대상인 하위 모듈을 호출하고, 하위 모듈에 파라미터를 전달하고, 테스트 수행 후의 결과를 도출하는 도구이다.

```
더미(Dummy)는 모조품, 가짜를 의미합니다. 하위 모듈의 테스트에 집중하기 위해 상위 모듈을 사용하지 않고 하위 모듈과 소통이 가능한 가짜 모듈을 임시로 쓰는 것이죠
```

## 하향식 통합 테스트

프로그램의 상위 모듈에서 하위 모듈 방향으로 통합하며 테스트한다.

### 절차

1. 주요 제어 모듈은 작성된 프로그램을 사용하고, 주요 제어 모듈의 종속 모듈들은 스텁(Stub)으로 대체한다.

2. 깊이 우선 또는 넓이 우선 등의 통합 방식에 따라 모듈을 통합하고 테스트를 실시한다.

3. 테스트 완료 후 하위 모듈인 스텁들이 실제 모듈로 교체된다.

4. 새로운 오류가 발생하지 않음을 보증하기 위해 회귀 테스트를 실시한다.

**스텁(Stub)** 일시적으로 필요한 조건만을 가지고 있는 실험용 모듈이다. 제어 모듈이 호출하는 타 모듈의 기능을 수행한다.

```
스텁을 사용하는 이유는 상위 모듈의 테스트에 집중하기 위해서입니다.
스텁이 실제 모듈로 교체되면 회귀 테스트를 통해 통합된 모듈을 테스트합니다.
```

## 테스트 기반 기준

- 명세 기반 테스트
- 구조 기반 테스트
- 경험 기반 테스트


**명세 기반 테스트** 사용자의 요구 사항에 대한 명세를 빠짐없이 테스트케이스로 만들어 구현하고 있는지 테스트한다.

예) 동등 분할, 경계 값 분석 등

**구조 기반 테스트** 소프트웨어 내부의 논리 흐름에 따라 테스트케이스를 작성하고 테스트한다.

예) 구문 기반, 결정 기반, 조건 기반 등

**경험 기반 테스트** 유사한 소프트웨어나 기술 등에 대한 테스트의 경험을 기반으로 테스트한다. 사용자의 요구사항에 대한 명세가 불충분하거나 테스트 시간에 제약이 있는 경우 효과적이다.

예) 에러 추정, 체크 리스트 


## 시각에 따른 테스트 분류

- 검증 테스트 (Verification)
- 확인 테스트 (Validation)

**검증 테스트** 개발자의 시각에서 제품의 생산 과정을 테스트한다. 제품이 명세서대로 완성됐는지 테스트한다.

**확인 테스트** 사용자의 시각에서 생산된 제품을 테스트한다. 사용자가 요구한대로 제품이 완성됐는지, 제품이 정상적으로 작동하는지를 테스트한다.


## 목적에 따른 테스트 분류

- 회복 테스트 (Recovery Test)
- 안전 테스트 (Security Test)
- 강도 테스트 (Stress Test)

- 회귀 테스트 (Regression Test)
- 병행 테스트 (Parallel Test)


## 성능 테스트

소프트웨어의 성능이나 효율성 등을 테스트한다

*성능 측정 지표*

- 처리량 (Throughput)
- 응답 시간 (Response Time)
- 경과 시간 (Turn-Around Time)
- 자원 사용률 (Resource Usage)

**처리량** 일정 시간 내에 애플리케이션이 처리하는 일의 양

**응답 시간** 애플리케이션에 요청을 전달한 시간부터 응답이 도착할 때까지 걸린 시간

**경과 시간** 애플리케이션에 작업을 의뢰한 시간부터 처리가 완료될 때까지 걸린 시간

**자원 사용률** 애플리케이션이 의뢰한 작업을 처리하는 동안에 사용한 자원의 양 (CPU 사용량, 메모리 사용량, 네트워크 사용량)등을 말한다.


### 성능 테스트 도구

애플리케이션의 성능을 테스트하기 위해 앱에 부하나 스트레스를 가하면서 성능 측정 지표를 점검하는 도구이다.

*종류*

- JMeter
- LoadUI
- OpenSTA

**JMeter** HTTP, FTP 등 다양한 프로토콜을 지원하는 부하 테스트 도구

**LoadUI** 서버 모니터링, Drag&Drop 등 사용자 편리성이 강화된 부하 테스트 도구이다. HTTP, JDBC등 다양한 프로토콜을 지원한다.

**OpenSTA** HTTP, HTTPS 프로토콜에 대한 부하 테스트 및 생산품 모니터링 도구


## Test Harness

테스트 환경.  
테스트를 위해 만들어진 명세서, 코드, 데이터 등을 포함한다.


### 테스트 하네스의 구성 요소

- Test Case 
- Test Suites (Test Scenario)
- Test Driver 
- Test Stub
- Mock Object
- Test Script


**Test Case** 사용자의 요구사항을 정확하게 준수했는지 여부를 확인하기 위한 테스트 명세서. 입력값, 실행조건, 기대 결과 등으로 구성된다.

**Test Suites** 테스트 케이스의 집합

**Test Driver** 테스트 대상인 하위 모듈을 호출하고, 파라미터를 전달하고, 테스트 후 결과를 도출하는 도구

**Test Stub** 제어 모듈이 호출하는 타 모듈의 기능을 수행한다. 일시적으로 필요한 조건만을 가지고 있는 테스트용 모듈

**Mock Object** 테스트에 필요한 사전에 정의된 행위를 수행하는 객체

**Test Script** 테스트 자동화를 위한 도구. 일정한 절차를 가지고 있다
