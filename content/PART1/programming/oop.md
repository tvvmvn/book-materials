# 객체 지향 프로그래밍 (OOP)

OOP는 객체지향 방법론을 구현한 프로그래밍 기법으로 객체와 클래스를 중심으로 코드를 작성합니다. 

다음은 OOP의 3가지 구성 요소입니다.

- 객체 (Object)
- 클래스 (Class)
- 메시지 (Message)

객체는 데이터와 함수로 구성됩니다. 데이터는 객체가 가진 정보이고 함수는 객체의 수행할 수 있는 연산입니다.

클래스는 객체의 설계도입니다. 클래스로부터 생성된 각각의 객체들을 클래스의 인스턴스라고 부릅니다.

메시지는 객체들 간의 상호작용에 사용되는 수단으로 객체의 동작이나 연산을 일으키는 외부의 요구사항입니다. 메시지를 받은 객체는 대응하는 연산을 수행하고 예상된 결과를 반환합니다. 

객체 지향의 구성 요소인 클래스, 객체, 메시지의 개념과 이들 간의 관계를 자동차에 비유해봅시다. 자동차의 '바퀴(객체)'는 자동차를 이루는 하나의 부품입니다. 이 바퀴는 '바퀴 설계도(클래스)'에 의해 제조됩니다. 운전자의 제어(메시지)에 따라 바퀴는 굴러가고 왼쪽 또는 오른쪽으로 회전할 수도 있고 정지 신호를 받으면 멈춥니다. 


# OOP의 4가지 특징

- 상속 (Inheritance)
- 추상화 (Abstraction)
- 다형성 (Polymorphism)
- 캡슐화 (Encapsulation)


상속은 상위 클래스의 모든 속성과 연산을 하위 클래스가 물려받는 것을 의미합니다. 하위 클래스는 상속받은 코드 외에도 자체적인 코드를 얼마든지 추가할 수 있습니다.
상속을 통해 코드를 재사용함으로서 프로그래밍의 효율성을 높일 수 있습니다.

추상화는 복잡한 내부 구현을 숨기고 쉽고 단순한 인터페이스만 노출시키는 것을 의미합니다. 추상화를 통해 모듈은 서로에 대해 자세히 알 필요가 없어지고 이는 모듈 간 결합도를 낮추는 역할을 합니다.

다형성은 말그대로 '다양한 형태를 가질 수 있는 성질'이라는 의미입니다. 객체 지향에서 다형성은 하나의 객체나 함수가 다양한 형태(능력)을 가질 수 있음을 의미합니다. 예를 들어 두 수를 더하고 결과를 출력하는 함수 add(x, y)가 있을 때, add는 정수형을 입력받든 실수형을 입력받든 모두 덧셈을 처리할 수 있는 능력을 가지고 있습니다. 만약 입력값에 따라 각자 다른 함수를 사용해야 한다면 프로그래밍의 복잡도가 증가할 것입니다.

캡슐화는 객체의 내부 정보를 보호하기 위해 마치 객체를 캡슐 속에 넣는 것에 비유할 수 있습니다. 외부에서 객체의 내부 정보에 접근할 때는 객체가 제공하는 인증된 인터페이스를 통해서만 접근할 수 있습니다.


# 객체지향 설계 원칙 (SOLID)

- 단일 책임 원칙 (SRP.Single Responsibility Principle)
- 개방-폐쇄 원칙 (OCP.Open-Closed Principle)
- 리스코프 치환 원칙 (LSP.Liskov Substitution Principle)
- 인터페이스 분리 원칙 (ISP.Interface Segregation Principle)
- 의존 역전 원칙 (DIP.Dependency Inversion Principle)


단일 책임 원칙은 '객체는 단 하나의 책임만 가져야 한다'라고 규정합니다. 예를 들어 식당에서 사장이 혼자 음식 조리, 계산, 서빙까지 한다면 식당이 효율적으로 돌아가지 않습니다(작은 식당은 가능하겠지만요). 요리사, 캐셔, 웨이터가 각자 맡은 역할을 할때 식당이 효율적으로 운영됩니다.

개방-폐쇄 원칙은 '확장에는 열려있고 수정에는 닫혀있어야 한다'라고 규정합니다. 결제 시스템을 생각해봅시다. 만약 새로운 결제 수단이 추가되는 경우 기존의 결제 시스템이 다시 사용될 경우를 고려해서 그대로 두고 확장된 결제 시스템으로 교체하는 것이 좋습니다. 

리스코프 치환 원칙은 '자식 클래스는 최소한 부모 클래스의 기능을 수행해야 한다'라고 규정합니다. 위의 예시와 연결해봅시다. 기존의 결제 시스템이 부모라면 확장된 결제 시스템은 자식입니다. 당연히 확장된 결제 시스템은 기존 결제 시스템의 모든 역할을 할 수 있어야 합니다.

인터페이스 분리 원칙은 '자신이 사용하지 않는 인터페이스에 영향을 받아서는 안된다'라고 규정합니다. 여러가지 기능을 가진 사무용 복합기를 떠올려봅시다. 만약 프린터만 하는 회사에서 복합기를 임대한다면 더 높은 임대 비용과 전기세 등을 감당해야 합니다. 프린터만 임대한다면 사용하지 않을 기능들로 인한 추가 비용을 지불할 필요가 없습니다.

의존 역전 원칙은 '한 클래스가 다른 클래스에 의존할 때 구체적인 클래스가 아닌 추상 클래스에 의존해야한다'라고 규정합니다. 예를 들어 노트북 브랜드가 자신들만의 충전기 인터페이스(구체적 클래스)를 개발한 경우를 생각해봅시다. 노트북 충전기가 망가졌는데 노트북 브랜드가 더 이상 사업을 하지 않는 경우 충전기가 없어지는 상황에 처합니다. 이런 경우를 대비하기 위해 제품 설계 시 USB-C 처럼 모든 브랜드에서 통용되는 충전기 규격(추상 클래스)을 따르는 것이 좋습니다.


# 객체 지향 분석 (OOA. Object Oriented Analysis)

객체 지향의 기본 요소인 클래스를 정의하고 식별하는 분석 활동입니다. 객체지향 프로그래밍의 사전 단계라고 볼 수 있습니다.

다음은 객체 지향 분석의 주요 방법론들입니다.

- Rumbaugh
- Booch
- Jacobson
- Coad & Yourdon
- Wirfs-Brock


# Rumbaugh

가장 대표적인 OOA 방법으로 그래픽을 적극적으로 활용하여 분석하는 기법입니다. 객체 모델링 기법(OMT. Object Modeling Technique)이라고도 합니다. 

분석 활동은 다음의 3단계 (객/동/기)로 이루어집니다.

1. 객체 모델링 (Object Modeling)
2. 동적 모델링 (Dynamic Modeling)
3. 기능 모델링 (Functional Modeling)

객체 모델링은 객체 다이어그램을 활용하여 시스템에서 요구되는 객체를 정의하고 객체들 간의 관계를 규정하는 활동입니다. 정보 모델링(Information Modeling)이라고도 합니다.

동적 모델링은 상태 다이어그램을 활용하여 상황에 따른 객체의 동작, 객체 간의 상호작용 등의 동적인 행위를 시간의 흐름에 따라 자연스럽게 표현하는 활동입니다.

기능 모델링은 자료 흐름도(DFD)를 활용하여 프로그램을 구성하는 자료들의 흐름을 중심으로한 모델링입니다.


# OOA 기타 방법론

부치 방법은 미시적 개발 프로세스와 거시적 개발 프로세스를 모두 사용합니다. 클래스와 객체들을 분석 및 식별하고 클래스의 속성과 연산을 정의합니다.

Jacobson 방법은 유스케이스(Usecase)를 주로 사용하는 방법입니다.

Coad & Yourdon 방법은 E-R 다이어그램을 활용하여 객체의 행위를 모델링합니다. 객체 식별, 구조 식별, 주제 정의, 속성과 인스턴스 연결 정의, 연산과 메시지 연결 정의 등의 과정으로 구성합니다.

Wirfs-Brock 방법은 분석과 설계 간의 구분이 없고 고객 명세서를 평가해서 설계 작업까지 연속적으로 수행하는 방법입니다.
